# Java 程序员的 IoT 协议入门（五）：手把手解析第一条 JT/T 808 报文

上一篇我们解析了一段位置数据。但设备实际发过来的，是这样一整条报文：

```
7E 02 00 00 25 01 38 00 13 80 00 00 07 00 00 00 00 00 00 00 03 01 57 FA F8
06 CC 62 89 00 1E 02 58 00 5A 26 10 20 08 30 05 01 04 00 00 30 39 31 01 0C F9 7E
```

这一篇我们一个字节都不落下，把它完整拆开。看懂了这一条，808 协议的整体结构你就掌握了一大半。

> 本文以 JT/T 808-2013 版为例。2019 版的消息头有一些变化，后面会专门写一篇讲两个版本的差异。

## 整体结构

808 的每一条报文都由四部分组成：

```
┌──────┬────────┬────────┬────────┬──────┐
│ 标识位 │  消息头  │  消息体  │  校验码  │ 标识位 │
│  7E  │ 12 字节 │ 长度可变 │  1 字节 │  7E  │
└──────┴────────┴────────┴────────┴──────┘
```

拿到一份新协议，**先找到这张整体结构图**，然后再逐个部分去看。这是读协议文档最重要的习惯。

## 第一步：找到首尾的 7E

`0x7E` 是标识位，标记一条报文的开始和结束。服务端收到数据后，第一件事就是找到一对 7E，把中间的内容切出来。

这里有个问题：**如果消息内容里正好也有 0x7E 怎么办？** 比如流水号恰好是 126（`0x007E`），解析时就会被误认为是报文结束了。

所以 808 规定了**转义规则**：

| 原始数据 | 发送时替换为 |
|---|---|
| `7E` | `7D 02` |
| `7D` | `7D 01` |

发送方在组包时把内容里的 7E、7D 替换掉，接收方收到后再还原回来。`7D` 自己也要转义，否则接收方就分不清一个 7D 到底是"真正的 7D"还是"转义的开始"。

这一条报文里恰好没有需要转义的字节，去掉首尾的 7E 后，剩下的就是原始内容：

```
02 00 00 25 01 38 00 13 80 00 00 07 | 00 00 00 00 ... 31 01 0C | F9
←────────── 消息头 12 字节 ─────────→ ←──── 消息体 37 字节 ────→  校验码
```

> 转义还原必须在校验之前做，校验码是对原始数据计算的。很多人第一次对接时校验总是失败，原因就是顺序搞反了。

## 第二步：验证校验码

校验码用的是 BCC 异或校验：**从消息头的第一个字节开始，到校验码之前的最后一个字节为止，所有字节依次做异或运算**，结果就是校验码。

```java
int bcc = 0;
for (int i = 0; i < data.length - 1; i++) {
    bcc ^= data[i];
}
bcc &= 0xFF;
// 计算结果是 0xF9，和报文最后一个字节一致，校验通过
```

校验不通过的报文要直接丢弃。这说明数据在传输过程中出错了，或者是组包的程序有 bug。

## 第三步：解析消息头

```
02 00 | 00 25 | 01 38 00 13 80 00 | 00 07
```

| 字节 | 字段 | 类型 | 值 | 含义 |
|---|---|---|---|---|
| `02 00` | 消息 ID | WORD | 0x0200 | 位置信息汇报 |
| `00 25` | 消息体属性 | WORD | 0x0025 | 见下文 |
| `01 38 00 13 80 00` | 终端手机号 | BCD[6] | 013800138000 | 设备的唯一标识 |
| `00 07` | 消息流水号 | WORD | 7 | 终端发出的第 7 条消息 |

### 消息 ID：这条报文是干什么的

808 用消息 ID 区分不同类型的消息。常见的几个：

| 消息 ID | 方向 | 含义 |
|---|---|---|
| 0x0100 | 终端 → 平台 | 终端注册 |
| 0x0102 | 终端 → 平台 | 终端鉴权 |
| 0x0002 | 终端 → 平台 | 终端心跳 |
| 0x0200 | 终端 → 平台 | 位置信息汇报 |
| 0x8001 | 平台 → 终端 | 平台通用应答 |
| 0x8100 | 平台 → 终端 | 终端注册应答 |

规律：**终端发给平台的消息 ID 以 0 开头，平台发给终端的以 8 开头**，很多对应的请求和应答只差最高位，比如注册 0x0100 和注册应答 0x8100。

### 消息体属性：一个 WORD 里塞了四个字段

`0x0025` 的二进制是 `0000 0000 0010 0101`，按位拆分：

| 位 | 含义 | 本例 |
|---|---|---|
| 0 ~ 9 | 消息体长度 | `00 0010 0101` = 37 |
| 10 ~ 12 | 数据加密方式，全 0 表示不加密 | 000，不加密 |
| 13 | 是否分包 | 0，不分包 |
| 14 ~ 15 | 保留 | 00 |

```java
int attr = 0x0025;
int bodyLength = attr & 0x03FF;           // 低 10 位：37
int encryption = (attr >> 10) & 0x07;     // 第 10~12 位：0
boolean subpackage = (attr >> 13 & 1) == 1;  // 第 13 位：false
```

这就是上一篇讲的位运算的实际用途。消息体长度只有 10 位，所以一条消息的消息体最多 1023 字节，超过这个长度就要分包发送（分包时消息头后面还会多出 4 个字节的分包信息，以后再讲）。

### 流水号：为什么需要它

终端每发一条消息，流水号就加 1。平台回复应答时会带上这个流水号，终端由此知道"平台确认收到的是我的哪一条消息"。

反过来，平台给终端下发指令时也有自己的流水号，终端应答时带回来，平台就能把应答和自己发出的指令对应上。这在后面实现"下发指令并等待结果"时非常关键。

## 第四步：解析消息体

消息 ID 是 0x0200，所以按照"位置信息汇报"的格式解析。消息体由**位置基本信息（28 字节）**和**位置附加信息（可变）**两部分组成。

### 位置基本信息

| 字节 | 字段 | 类型 | 解析 |
|---|---|---|---|
| `00 00 00 00` | 报警标志 | DWORD | 0，无报警 |
| `00 00 00 03` | 状态 | DWORD | ACC 开、已定位、北纬、东经 |
| `01 57 FA F8` | 纬度 | DWORD | 22543096 ÷ 10⁶ = 22.543096° |
| `06 CC 62 89` | 经度 | DWORD | 114057865 ÷ 10⁶ = 114.057865° |
| `00 1E` | 高程 | WORD | 30 米 |
| `02 58` | 速度 | WORD | 600 ÷ 10 = 60.0 km/h |
| `00 5A` | 方向 | WORD | 90°（正北为 0，顺时针），即正东 |
| `26 10 20 08 30 05` | 时间 | BCD[6] | 2026-10-20 08:30:05 |

这部分在上一篇里已经详细讲过了。注意经纬度本身都是正数，南纬、西经是通过状态字段的第 2、3 位来表示的。

### 位置附加信息

基本信息之后，还剩 9 个字节：

```
01 04 00 00 30 39 | 31 01 0C
```

附加信息是一个列表，每一项的格式都是：

```
┌────────┬────────┬────────────┐
│ ID 1 字节│长度 1 字节│ 内容（长度字节）│
└────────┴────────┴────────────┘
```

这种格式通常称为 **TLV**（Type-Length-Value）。它的好处是：遇到不认识的 ID，按长度直接跳过就行，不影响解析后面的项。协议升级时新增附加信息，老平台也不会因此解析出错。

| 字节 | ID | 长度 | 内容 | 含义 |
|---|---|---|---|---|
| `01 04 00 00 30 39` | 0x01 | 4 | 12345 | 里程，单位 1/10 km，即 1234.5 km |
| `31 01 0C` | 0x31 | 1 | 12 | GNSS 定位卫星数：12 颗 |

```java
while (body.isReadable()) {
    int id = body.readUnsignedByte();
    int length = body.readUnsignedByte();
    ByteBuf value = body.readSlice(length);
    switch (id) {
        case 0x01: mileage = value.readUnsignedInt() / 10.0; break;
        case 0x31: satellites = value.readUnsignedByte(); break;
        default:   break;  // 不认识的附加信息直接跳过
    }
}
```

## 完整解析结果

```
消息 ID：0x0200 位置信息汇报
终端手机号：013800138000
流水号：7
报警：无
状态：ACC 开、已定位
位置：北纬 22.543096°，东经 114.057865°，高程 30 米
速度：60.0 km/h，方向：正东
时间：2026-10-20 08:30:05
里程：1234.5 km
卫星数：12
```

## 平台还要做什么：回复应答

收到位置汇报后，平台需要回复一条**平台通用应答（0x8001）**，告诉终端"我收到了"，内容是：应答流水号（7）、应答的消息 ID（0x0200）、结果（0 表示成功）。

如果终端迟迟收不到应答，会按照协议规定的间隔重发。**平台不回应答，终端就会一直重发，平台就会收到大量重复数据**，这也是新手常犯的错误之一。

## 小结

解析一条 808 报文，固定的步骤是：

1. 找到首尾的 7E，切出一帧
2. 还原转义
3. 验证校验码
4. 解析消息头，根据消息 ID 决定消息体怎么解析
5. 解析消息体
6. 回复应答

前三步是所有 808 消息通用的，在 Netty 里通常放在帧解码器中完成。但这里有个前提：**我们每次从网络上收到的数据，正好是一条完整的报文吗？**

答案是：不一定。这就是下一篇要讲的 TCP 拆包粘包问题。
