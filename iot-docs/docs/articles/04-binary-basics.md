# Java 程序员的 IoT 协议入门（四）：二进制基础，读协议的第一关

前三篇讲的是概念，从这一篇开始动手。

打开任何一份设备协议文档，你都会看到这样的字段表：

| 字段 | 数据类型 | 说明 |
|---|---|---|
| 报警标志 | DWORD | 按位定义，见表 X |
| 纬度 | DWORD | 以度为单位的纬度值乘以 10 的 6 次方 |
| 速度 | WORD | 1/10 km/h |
| 时间 | BCD[6] | YY-MM-DD-hh-mm-ss |

再看设备发来的数据：

```
00 00 00 00 00 00 00 03 01 57 FA F8 06 CC 62 89 00 1E 02 58 00 5A 26 10 20 08 30 05
```

要把这两者对应起来，需要掌握几个基础知识。平时写业务代码基本用不到，但做设备接入时每天都会用到。

## 1. 十六进制：为什么协议里全是 0x7E 这种东西

一个字节是 8 位二进制，比如 `01111110`。直接写二进制太长，写十进制（126）又看不出每一位的情况，所以协议里统一用十六进制：**每 4 位二进制对应 1 位十六进制，1 个字节正好是 2 位十六进制**。

```
二进制    0111 1110
十六进制    7    E     → 0x7E
十进制    126
```

所以看到 `00 1E` 这两个字节，你要能反应过来：这是一个 2 字节的数，`0x001E` = 30。

**几个必须熟悉的数据类型**（几乎所有国标协议都这么定义）：

| 类型 | 长度 | Java 里用什么接 |
|---|---|---|
| BYTE | 1 字节，无符号 | `int`（`readUnsignedByte()`） |
| WORD | 2 字节，无符号 | `int`（`readUnsignedShort()`） |
| DWORD | 4 字节，无符号 | `long`（`readUnsignedInt()`） |
| BYTE[n] | n 字节 | `byte[]` |
| BCD[n] | n 字节 BCD 码 | `String` |
| STRING | GBK 编码的字符串 | `String` |

注意最后一列，为什么 DWORD 要用 `long` 来接？这就引出了 Java 程序员遇到的第一个坑。

## 2. Java 没有无符号数

C 语言有 `unsigned char`、`unsigned int`，而 Java 的 `byte`、`short`、`int`、`long` **全都是有符号的**。

```java
byte b = (byte) 0xFF;
System.out.println(b);          // 输出 -1，不是 255
System.out.println(b & 0xFF);   // 输出 255
```

`byte` 的范围是 -128 ~ 127，而协议里的 BYTE 是 0 ~ 255。超过 127 的值，用 `byte` 存就变成了负数。

**解决办法**：用更大的类型来存，并且和掩码做与运算。

```java
int  u8  = b & 0xFF;              // BYTE  → int
int  u16 = s & 0xFFFF;            // WORD  → int
long u32 = i & 0xFFFFFFFFL;       // DWORD → long，注意末尾的 L
```

最后一行是很多人会忘的：DWORD 的最大值是 42 亿多，超过了 `int` 的上限（21 亿多），必须用 `long`。比如报警标志的最高位是 1 时，用 `int` 读出来就是负数，后续的判断全错。

好在 Netty 的 `ByteBuf` 已经提供了现成的方法：`readUnsignedByte()`、`readUnsignedShort()`、`readUnsignedInt()`，直接用就行。

## 3. 位运算：一个字节表示 8 个开关

为了省流量，协议里经常用一个数的每一位表示一个状态。比如 808 协议中的状态字段（DWORD）：

| 位 | 含义 |
|---|---|
| 0 | 0：ACC 关；1：ACC 开（车辆点火） |
| 1 | 0：未定位；1：已定位 |
| 2 | 0：北纬；1：南纬 |
| 3 | 0：东经；1：西经 |
| …… | …… |

收到状态值 `0x00000003`，二进制是 `...0000 0011`，说明第 0 位和第 1 位是 1：**ACC 开、已定位、北纬、东经**。

用代码判断某一位：

```java
long status = 0x00000003L;

boolean accOn   = (status & 1) != 0;          // 第 0 位
boolean located = (status & (1 << 1)) != 0;   // 第 1 位
boolean south   = (status >> 2 & 1) == 1;     // 第 2 位
```

两种写法都很常见：`status & (1 << n)` 是用掩码去"套"第 n 位；`status >> n & 1` 是把第 n 位移到最低位再取出来。

反过来，**设置**某一位：

```java
status |= 1 << 1;      // 第 1 位置 1
status &= ~(1 << 1);   // 第 1 位置 0
```

**练习**：报警标志的值是 `0x00000005`，哪几位是 1？

## 4. 大端和小端：同一个数，两种写法

`0x12345678` 这个 4 字节的数，在内存或网络中有两种存放顺序：

```
大端（Big-Endian）：   12 34 56 78     高位字节在前，和我们书写的顺序一致
小端（Little-Endian）：78 56 34 12     低位字节在前
```

规律：

- **国标协议基本都是大端**，JT/T 808、1078、32960 都是（这也叫"网络字节序"）
- **Java 和 Netty 默认也是大端**，`readInt()` 就是按大端读，所以对接国标协议时不需要做任何处理
- **但很多私有协议是小端**，因为设备端的单片机大多是小端架构，嵌入式工程师直接把内存里的结构体发出来，就成了小端。Netty 也有对应的方法：`readIntLE()`、`readUnsignedShortLE()`
- **MODBUS 是个特例**：数据是大端，但 CRC 校验码是低字节在前

对接新协议时，如果文档没写清楚字节序，可以对着一条报文验算一下：比如已知长度字段的值是 37，看报文里写的是 `00 25` 还是 `25 00`。

## 5. BCD 码：用十六进制的样子写十进制

终端手机号 `13800138000`，在 808 报文里是这样的：

```
01 38 00 13 80 00
```

看起来就像是把数字直接"写"进了十六进制里。这就是 **BCD 码**：每 4 位表示一个十进制数字（0~9），1 个字节存 2 位数字，位数不够时左边补 0。

时间也一样，`2026-10-20 08:30:05` 写成：

```
26 10 20 08 30 05
```

注意，`0x26` 在这里不能当成十六进制数（38）来理解，它表示的就是数字"26"。

用代码读取：

```java
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 6; i++) {
    int b = buf.readUnsignedByte();
    sb.append(b >> 4).append(b & 0x0F);  // 高 4 位、低 4 位各是一个数字
}
// sb = "013800138000"
```

一个实际项目中的小坑：终端还没定位成功时，经常上报全 0 的时间 `00 00 00 00 00 00`，如果直接转成日期就会报错。仓库里的 `BcdUtils.readBcdTime()` 对这种情况返回了 `null`。

## 6. 定点小数：协议里没有 float

再看纬度字段：DWORD，"以度为单位的纬度值乘以 10 的 6 次方"。

报文中是 `01 57 FA F8`，转成十进制是 22543096，除以 1000000，就是 **22.543096°**。

协议里很少直接传浮点数，而是乘以一个倍数变成整数来传。原因是浮点数的二进制格式在不同平台上可能有差异，整数则没有任何歧义。

同理，速度"1/10 km/h"的意思是：报文中的值除以 10 才是真实速度。`02 58` = 600，表示 60.0 km/h。

**读文档时一定要看清楚单位和倍数**，这是数据"看起来对、其实错了 10 倍"的最常见原因。

## 回到开头那串字节

现在你已经可以把开头那段数据解析出来了：

```
00 00 00 00   报警标志：0，没有报警
00 00 00 03   状态：ACC 开、已定位、北纬、东经
01 57 FA F8   纬度：22543096 → 22.543096°
06 CC 62 89   经度：114057865 → 114.057865°
00 1E         高程：30 米
02 58         速度：600 → 60.0 km/h
00 5A         方向：90，正东
26 10 20 08 30 05   时间：2026-10-20 08:30:05
```

这正是 JT/T 808 协议中一条位置上报的消息体。下一篇，我们把完整的报文（包括外面的帧头、消息头、校验码）一起拆开来看。

## 练习答案

`0x00000005` = 二进制 `0101`，第 0 位和第 2 位是 1。在 808 协议中，报警标志的第 0 位是紧急报警，第 2 位是疲劳驾驶。
