# Java 程序员的 IoT 协议入门（二）：设备是怎么连上平台的

上一篇讲了物联网平台的整体结构。这一篇回答一个很实际的问题：**设备的数据，到底是通过什么方式发到平台的？**

接手项目时，第一件要搞清楚的事情就是这个。方式不同，平台的写法完全不一样。

## 先看全貌

国内项目里最常见的几种方式：

| 方式 | 典型设备 | 平台需要做什么 |
|---|---|---|
| TCP 长连接 + 私有/国标协议 | 车载终端、环保数采仪、充电桩 | 自己写 TCP 服务端，自己解析协议 |
| DTU 透传 | 工业现场的 PLC、电表、传感器 | 同上，只是数据外面多了一层 DTU |
| MQTT | 智能家居、新一代的智能硬件 | 搭 MQTT Broker 或者使用云平台，订阅主题 |
| HTTP | 低频上报的设备、带操作系统的设备 | 写普通的接口就行 |
| UDP / CoAP | NB-IoT 水表、燃气表 | 写 UDP 服务端，或者对接运营商的物联网平台 |

下面一个一个说。

## 一、TCP 长连接：国内项目的主流

设备开机后，主动连接平台的 IP 和端口，建立一条 TCP 连接，然后就一直保持着：

```
设备                                   平台
 │  ──── TCP 三次握手 ──────────────►  │
 │  ──── 注册 / 登录 ───────────────►  │
 │  ◄─── 登录应答 ──────────────────  │
 │  ──── 心跳（每 30 秒）───────────►  │
 │  ──── 位置上报（每 10 秒）────────►  │
 │  ◄─── 平台下发：拍照指令 ─────────  │
 │  ──── 拍照结果 ──────────────────►  │
 │            ……一直保持……             │
```

**为什么国内这么多设备用 TCP？**

- 协议简单，嵌入式端实现成本低，几 KB 内存的单片机都能跑
- 二进制格式省流量。一条位置数据用 JSON 要 200 多字节，用二进制只要 30~50 个字节。几万台设备一个月下来，流量费差别非常大
- 历史原因：很多国家标准和行业标准是十几年前制定的，当时 MQTT 还没普及，比如车联网的 JT/T 808、环保的 HJ212，用的都是 TCP

**对平台的要求**：

- 自己用 Netty 写 TCP 服务端
- 自己处理拆包粘包（第六篇专门讲）
- 自己解析协议、管理会话、检测心跳

这也是这个系列的重点。**能搞定 TCP 长连接接入，其他方式都只是它的简化版。**

## 二、DTU 透传：工业现场最常见

工厂、水厂、配电房里的设备，很多都不能直接联网，它们只有 RS485 串口，说的是 Modbus 之类的串口协议。

这时候就要在旁边加一个 **DTU**（数据传输单元），一个巴掌大的小盒子：

```
 电表 ──RS485──► DTU ──4G / TCP──► 平台
                 ↑
       把串口数据原样转发到 TCP，不做任何解析，所以叫"透传"
```

透传对平台意味着：**TCP 连接是 DTU 建立的，但数据内容是电表发出来的。**

几个常见的坑：

- **注册包和心跳包**：DTU 连上平台后，通常会先发一个注册包（比如 DTU 的 IMEI 号），平时还会发心跳包。它们的格式由 DTU 厂家定义，和电表的协议完全无关，平台要把它们和电表数据区分开
- **一条连接对应多台设备**：一个 DTU 下面可能挂了好几块电表，靠 Modbus 的从站地址来区分
- **轮询模式**：Modbus 是一问一答的，电表不会主动上报，需要平台定时发查询指令

我在园区和环卫项目里都用过 DTU，空气质量、电表、水表这些设备基本都是这么接的。印象最深的是两件事：

**注册包一家一个样。** 有的 DTU 连上来先发一串 ASCII 的 IMEI，有的发一个带自己帧头的十六进制包，还有的什么都不发，要在 DTU 的配置软件里手动打开。项目里换了一批 DTU，注册包格式变了，平台认不出是谁，数据全部"无主"。后来平台这边把注册包的解析做成了可配置的，按 DTU 型号选。

**轮询间隔不是越短越好。** 一条 485 总线上挂着好几台设备，同一时间只能一问一答，经过 4G 一来一回就是几百毫秒。间隔设得太短，上一轮还没问完下一轮就开始了，请求越积越多。空气质量、电量这类数据，分钟级就够用，没必要几秒一次。

## 三、MQTT：越来越多的新设备在用

MQTT 是专门为物联网设计的发布 / 订阅协议：

```
        发布 sensor/001/data                      订阅 sensor/+/data
设备 ─────────────────────────► MQTT Broker ─────────────────────► 平台
     ◄───────────────────────────            ◄────────────────────
        订阅 sensor/001/cmd                       发布 sensor/001/cmd
```

和 TCP 自定义协议相比：

| | TCP + 自定义协议 | MQTT |
|---|---|---|
| 拆包粘包 | 自己处理 | 协议已经处理好了 |
| 心跳、重连 | 自己约定 | 协议自带 |
| 消息可靠性 | 自己设计应答机制 | QoS 0 / 1 / 2 |
| 数据格式 | 二进制 | 随意，通常是 JSON |
| 平台开发量 | 大 | 小，用 EMQX 等现成的 Broker |

看起来 MQTT 全面占优，那为什么 TCP 自定义协议还没被淘汰？一是存量设备太多，二是国家标准和行业标准规定了必须用某种协议。比如营运车辆要接入政府监管平台，就必须遵循 JT/T 808，设备厂家没得选。

**所以现实情况是：新设备越来越多地用 MQTT，但接国标协议、接老设备，TCP 是绕不开的。** 而且你搞懂了 TCP 协议接入，再看 MQTT 会发现它只是把这些工作标准化了，学起来非常轻松。

## 四、HTTP：最简单，但很少用

有些设备直接通过 HTTP 调用平台接口上报数据，比如每小时上报一次的环境监测设备，或者本身就运行 Android、Linux 的设备。

平台这边就是写普通的接口。但它有两个明显的限制：

- **平台没法主动找设备**。设备不来请求，平台就没办法给它下发指令，只能等它下次请求时，在响应里顺便带上指令
- **开销大**。每次都要建立连接，HTTP 头也很占流量，不适合高频上报

## 五、UDP / CoAP：NB-IoT 设备

水表、燃气表、烟感这类设备，靠电池要工作好几年，不可能一直保持 TCP 连接。它们大多使用 NB-IoT 网络，用 UDP 或者基于 UDP 的 CoAP 协议，平时休眠，定时醒来上报一次就继续休眠。

这类设备有两种接入方式：一是平台自己写 UDP 服务端；二是设备先接入运营商的物联网平台，再由运营商平台把数据推送给我们。后者在国内很常见，对平台来说就变成了"对接一个 HTTP 推送接口"。

## 接手项目时，先问清楚这几个问题

1. 设备通过什么方式联网？4G、有线、NB-IoT，还是经过 DTU？
2. 连接是谁发起的？设备连平台，还是平台连设备？（极少数设备是平台主动去连）
3. 用的是什么协议？国家标准、行业标准、厂家私有协议，还是 MQTT？**一定要拿到协议文档和真实报文样例**
4. 有多少台设备？上报频率是多少？这决定了平台要按什么规模来设计
5. 平台需不需要给设备下发指令？需要的话，设备离线时指令怎么处理？

把这几个问题问清楚，项目的技术方案基本就有了一半。

## 小结

- 国内项目里，**TCP 长连接 + 二进制协议**是绝对的主流，也是最需要专门学习的部分
- DTU 透传本质上也是 TCP，只是要多处理一层 DTU 的注册包和心跳
- MQTT 帮你处理了很多底层工作，新设备用得越来越多
- HTTP 和 UDP 各有适用场景，但都比较简单
